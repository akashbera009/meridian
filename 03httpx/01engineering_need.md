Why it matters for AI engineering specifically

Most of what you're building — agent loops like basic_agent.py, RAG pipelines, batch processing over documents, multi-tool agents — involves firing off many HTTP requests to LLM/embedding APIs (OpenAI, Groq, Anthropic, vector DBs, etc.), often concurrently. requests is synchronous and blocking by design; it was built for scripts that make one call at a time. That mismatch shows up fast once you're doing real work:

1. Connection pooling — every HTTP request has overhead: DNS lookup, TCP handshake, TLS handshake. If you call an API 50 times in a loop with requests, and you're not careful, you can end up re-establishing connections repeatedly. httpx.AsyncClient (like requests.Session, but async) reuses connections across calls to the same host — meaningful savings when you're hitting api.groq.com or api.openai.com dozens/hundreds of times per run.

2. Async = actual concurrency — this is the big one. If you need to call an LLM for 20 documents in a RAG pipeline, requests forces you to do them one at a time (or hack around it with threads). With httpx.AsyncClient inside an asyncio program (exactly like the coroutinesio.py/TaskGroup pattern you were just looking at), you can fire all 20 requests concurrently and just wait on I/O — since LLM calls are mostly waiting on the network/model, not CPU-bound, this is a massive latency win. A batch that takes 60 seconds sequentially might take 3-4 seconds concurrently.

3. Timeouts — LLM APIs can hang or be slow (a model generating a long response, a provider having a bad day). requests technically supports timeouts but people often forget to set them, and a hung request with no timeout can block your whole pipeline indefinitely. httpx makes timeout configuration more explicit and has good defaults, plus separate connect/read/write timeout granularity — useful because "connecting" failing vs. "the model is just slow to stream" are different problems you want to handle differently.

4. Retries — LLM APIs rate-limit you (429s) or occasionally 5xx. In production agent/RAG code, you basically always want retry-with-backoff logic. httpx plays nicely with retry libraries (like tenacity) and transport-level retry configuration, whereas bolting retries onto raw requests calls is more manual.

The practical takeaway for your career stage: the OpenAI/Groq/Anthropic Python SDKs (which you're already using via client.chat.completions.create) are themselves built on top of httpx under the hood — so understanding httpx.AsyncClient isn't just "a nicer requests," it's understanding the actual transport layer your LLM SDKs are using. Once you're building agents that need to be fast under concurrent load (multiple users, multiple tool calls in parallel, batch document processing), reaching for requests becomes a real bottleneck, and "I know how to write async HTTP clients with pooling/timeouts/retries" is a legitimate signal of production-readiness in an AI engineering interview or job.
